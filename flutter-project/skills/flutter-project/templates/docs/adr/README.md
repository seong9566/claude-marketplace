# 결정 로그 (ADR)

이 앱의 **"왜 이렇게 되어 있나"** 결정을 1건 = 1파일로 기록한다. 코드만 클론한 에이전트·사람도 결정 맥락을 회수할 수 있게 하는 in-repo 정본이다.

## 무엇이 ADR이고 무엇이 아닌가
- **ADR (여기)** — 아키텍처·제품 전제·보안 경계 등 일회성 결정 + 근거 + 대안. 예: "왜 Clean Architecture", "왜 기본 폴백 제거".
- **반복 코딩 규칙 (ADR 아님)** — `docs/ARCHITECTURE.md`로. 예: dispose에서 ref.read 금지, 색 토큰 사용법.

## 규칙
- 파일명: `NNNN-kebab-제목.md` (번호는 증가, 재사용 금지).
- 한 결정은 한 파일. 파일은 짧게(맥락·결정·근거·영향, ~25-35줄). 이력이 쌓여도 단일 read가 커지지 않게 분리한다.
- 결정이 바뀌면 기존 파일을 지우지 말고 상태를 `Superseded by ADR-NNNN`으로 바꾸고 새 파일을 추가한다.
- 새 ADR 추가 시 아래 인덱스에 **한 줄**만 등록한다. 템플릿: [`_template.md`](_template.md).

## 상태 전이 — 언제 폐기/교체하나
폐기는 주기적 청소가 아니라 **반대되는 새 결정을 내리는 그 순간** 일어난다(반응적). ADR 본문은 사후에 고치지 않는다.

- **Accepted → Superseded by ADR-NNNN**: 새 결정이 기존 "무엇"을 뒤집을 때. 같은 변경에서 새 ADR(새 번호)을 쓰고 기존 파일의 **상태 줄만** 바꾼다.
- **Accepted → Deprecated**: 그 결정이 다루던 대상이 사라졌을 때(예: 기능 제거) — 대체 결정이 없는 경우.
- **상태 안 바뀜**: 오타·링크·출처 보강 같은 사소한 수정, 결정을 따르는 코드 리팩터·구현 진행 → 본문 그대로, Accepted 유지.

새 결정이 기존 결정을 뒤집는다면 새 ADR을 추가하는 변경에서 기존 ADR의 상태도 함께 바꾼다.
